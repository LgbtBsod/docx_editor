## Критические риски

1. ✅ **XSS/HTML injection в письмах (Critical)** — **закрыто (v1)**
   - Реализована клиентская санитизация HTML и серверная санитизация перед `create_document`.
   - Остаточный риск: желательно перейти на более строгий allowlist sanitizer (например, policy-based).

2. ✅ **Небезопасная отправка ссылок в письмах (High)** — **закрыто (v1)**
   - Введена нормализация и запрет небезопасных схем.
   - На сервере ссылки без `https` отбрасываются.

3. 🟡 **Потенциальная утечка персональных данных через открытый поиск получателей (High)** — **в продакшн-подготовке**
   - Уже реализовано: auth-check, `maxTop`, min search length, wildcard-block, client throttling, аудит term-hash.
   - Остаток: подключить полноценный runtime-entityset и включить мониторинг аномалий в продуктивной системе.

## Высокие/средние архитектурные риски

## Что можно вынести в SAP HANA (рекомендуется)

С учетом того, что backend на HANA, часть вычислительной/агрегирующей нагрузки стоит переносить ближе к БД:

1. **Дедупликация и нормализация получателей на SQL/CDS уровне**
   - Делать `LOWER(email)` + `DISTINCT`/группировку в CDS view для списков перед отправкой.

2. **Постраничный поиск получателей с лимитами**
   - Серверные `TOP/OFFSET` (или аналог OData paging) + ограничение max page size.

3. **Агрегации preflight-метрик**
   - Подсчет количества адресатов/дубликатов/доменных групп по email в CDS/HANA, а не циклами в UI.

4. **История и отчеты отправок**
   - Вынос аналитики статусов отправки и ошибок в CDS analytical views для быстрых дашбордов.

5. **Поиск по правам доступа**
   - Логику фильтрации по auth-object и организационным срезам по возможности фиксировать в CDS с параметрами.

## Новый аудит перед продуктивным запуском (2026-05-19)

### Слабые стороны, мешающие go-live

1. **Неполная runtime-реализация OData в DPC_EXT**
   - В `get_entityset/create_entity` остаются scaffold-TODO, нет полноценного payload mapping и серверной бизнес-валидации всех полей.

2. **Нет retry/idempotency на уровне API отправки**
   - Повторные запросы клиента могут привести к повторной рассылке при сетевых сбоях.

3. **Security-аудит не интегрирован в BAL/операционный контур**
   - Есть запись hash-событий в таблицу, но нет централизованной операционной отчетности и алертинга.

4. **Legacy editor (`document.execCommand`)**
   - Функционально работает, но технологически устаревший путь с рисками совместимости браузеров.

5. **Нет CI/security regression контура**
   - Отсутствуют автоматизированные проверки ABAP/OData и нагрузочные smoke/regression сценарии.

### Что начали устранять в этом шаге

- Добавлен backend-limit на количество получателей в `send_mass_mail` (5000 на запрос) для защиты от перегрузки и массовых ошибок при отправке.

## Итоговое архитектурное ревью (дополнение от 2026-05-19)

### Ключевой вывод

**Нет, разработка не завершена для продуктивного запуска.**
Кодовая часть значительно усилена, но остаются обязательные go-live пункты, которые сейчас либо не реализованы, либо требуют ландшафтных действий в SAP.

### Новые находки (gap list)

1. **Риск неконсистентности статусов отправки на уровне OData/UI**
   - В текущей реализации нет полноценной модели статусов пакетов/получателей в API-ответе (`NEW/SENT/FAILED/RETRY` по каждому email) и нет post-send отчета для оператора.

2. **Idempotency на уровне API отправки не завершена**
   - Retry в BCS реализован, но нет контрактного `Idempotency-Key` и дедупликации повторных create-запросов на уровне OData/DB.

3. **Security-аудит пока технический, но не операционный**
   - Есть запись hash-событий в таблицу, но нет BAL/SLG1 корреляции, SLA-алертов и регламентированного расследования аномалий.

4. **Policy-based sanitizer отсутствует**
   - Используется regex-подход; для production-security baseline рекомендуется строгая allowlist-политика с тестовым набором payload.

5. **Не закрыт migration-риск редактора**
   - `document.execCommand` остается технологическим долгом и риском совместимости браузеров/поддержки.

6. **Нет автоматизированного quality-gate**
   - В репозитории отсутствуют CI/ATC/security regression сценарии для ABAP/OData/UI.

### Рекомендованное go-live решение

- **Go-live только с условием**: закрыть пункты по idempotency, post-send отчетности, операционному audit-контуру и security baseline (CSRF/CORS/SICF/TLS) в целевом ландшафте.
- **Кодовую часть считать “feature-complete”, но не “production-complete”** без инфраструктурных и эксплуатационных мер.

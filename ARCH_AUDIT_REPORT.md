## Критические риски

1. ✅ **XSS/HTML injection в письмах (Critical)** — **закрыто (v1)**
   - Реализована клиентская санитизация HTML и серверная санитизация перед `create_document`.
   - Остаточный риск: желательно перейти на более строгий allowlist sanitizer (например, policy-based).

2. ✅ **Небезопасная отправка ссылок в письмах (High)** — **закрыто (v1)**
   - Введена нормализация и запрет небезопасных схем.
   - На сервере ссылки без `https` отбрасываются.

3. 🟡 **Потенциальная утечка персональных данных через открытый поиск получателей (High)** — **частично**
   - Требуется финализировать на OData/DPC уровне: auth-check + hard-limit + throttling + аудит запросов.

## Высокие/средние архитектурные риски

4. ⏳ **Использование устаревшего `document.execCommand` (Medium)**
   - Не закрыто. Нужна миграция на современный редакторный компонент.

5. ✅ **Слишком упрощенная email-валидация (Medium)** — **закрыто (v1)**
   - Regex усилен на сервере и preflight-проверкой на клиенте.

6. 🟡 **Пакетная отправка с `i_with_error_screen = 'X'` (Medium)** — **частично**
   - Нужна доработка для фоновых массовых сценариев (без UI dependency) и операционный retry policy.

7. ✅ **Отсутствие ограничений на размер/тип вложений (High)** — **закрыто (v1)**
   - На UI добавлены лимиты размера и allowlist MIME + preflight блокировка отправки.
   - Рекомендуется добавить зеркальные серверные лимиты в DPC/BCS слой.

## UX/UI проблемы

8. ⏳ **Перегрузка одного экрана сценариями разной сложности (Medium)**
   - Не закрыто. Требуется мастер-поток (wizard).

9. ✅ **Слабая обратная связь перед отправкой массового письма (High)** — **закрыто (v1)**
   - Реализован preflight gate: невалидные/дубликаты email, размер вложений, небезопасные ссылки, опасный HTML.
   - Следующий шаг: визуальный preflight-экран с полным резюме перед подтверждением.

10. ⏳ **Неочевидное управление контент-источниками (Medium)**
   - Не закрыто полностью. Нужны дополнительные guard-dialogs и стратегия «draft protection».

## Что можно вынести в SAP HANA (рекомендуется)

С учетом того, что backend на HANA, часть вычислительной/агрегирующей нагрузки стоит переносить ближе к БД:

1. **Дедупликация и нормализация получателей на SQL/CDS уровне**
   - Делать `LOWER(email)` + `DISTINCT`/группировку в CDS view для списков перед отправкой.

2. **Постраничный поиск получателей с лимитами**
   - Серверные `TOP/OFFSET` (или аналог OData paging) + ограничение max page size.

3. **Агрегации preflight-метрик**
   - Подсчет количества адресатов/дубликатов/доменных групп по email в CDS/HANA, а не циклами в UI.

4. **История и отчеты отправок**
   - Вынос аналитики статусов отправки и ошибок в CDS analytical views для быстрых дашбордов.

5. **Поиск по правам доступа**
   - Логику фильтрации по auth-object и организационным срезам по возможности фиксировать в CDS с параметрами.

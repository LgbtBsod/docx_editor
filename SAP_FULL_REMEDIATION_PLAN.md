### Что не удается закрыть полностью в этом репозитории и почему

1. **Gateway runtime security baseline (CSRF/CORS/TLS/SICF)** — требует изменений в целевом SAP Gateway landscape (транзакции/админ-настройки), а не в файлах репозитория.
2. **Полноценная реализация DPC_EXT бизнес-логики с парсингом payload и OData mapping** — в репозитории отсутствуют generated базовые классы DPC/MPC и runtime-контекст сервиса, поэтому добавлен только корректный scaffold.
3. **Интеграция с BAL/SLG1 и продуктивным аудит-хранилищем** — требует подключения к SAP системе и транспорта DDIC-объектов/настроек логирования.
4. **AV/Content malware scanning** — зависит от внешней корпоративной инфраструктуры и интеграционных точек, которых нет в локальном проекте.
5. **Нагрузочные и security regression в CI** — отсутствует CI pipeline и test harness для ABAP/OData в текущем репозитории.

## 1. Безопасность доступа и защита ПДн (P0)

### 1.1. Серверная авторизация на OData-операциях
**Что нужно исправить:**
- На уровне DPC_EXT реализовать явные `AUTHORITY-CHECK` для чтения/поиска получателей, отправки массовых писем, CRUD шаблонов и вложений.
- Разделить роли минимум на: `MM_MAIL_VIEW`, `MM_MAIL_SEND`, `MM_MAIL_ADMIN`.
- Отвязать решение от implicit-допусков через UI: backend должен быть источником истины по правам.

**Что реализовать для закрытия подпункта:**
1. Добавить checks в методы `*_GET_ENTITYSET`, `*_CREATE_ENTITY`, `*_UPDATE_ENTITY`, `*_DELETE_ENTITY`.
~~2. Для отказа возвращать корректные OData-ошибки `403 Forbidden` с безопасным текстом.~~
3. Добавить ABAP Unit/интеграционные тест-кейсы «нет роли → отказ», «роль есть → доступ».
4. Зафиксировать матрицу ролей и объектов авторизации в техдоке.

**Критерий закрытия:**
- Любой неавторизованный пользователь получает отказ на backend независимо от UI-клиента.

---

### 1.2. Anti-enumeration для поиска получателей
**Что нужно исправить:**
- Закрыть риск массового перебора/выгрузки email-адресов через поиск.

**Что реализовать для закрытия подпункта:**
~~1. Минимальная длина поискового запроса (например, 3+ символа).~~
2. Hard-limit на размер страницы (например, max 50/100).
3. Пагинация (`$top/$skip`) с серверным `maxTop`.
4. Ограничение частоты запросов на пользователя/сессию.
5. Блокировка wildcard-only запросов (`%`, `_`, пустой/односимвольный шум).
6. Логирование поисковых запросов (кто, когда, term-hash, размер выдачи).

**Критерий закрытия:**
- Невозможно выгрузить справочник сотрудников через серию широких запросов; аномалии видны в аудит-логах.

---

### 1.3. Защита персональных данных в логах и ответах
**Что нужно исправить:**
- Исключить утечки email/ФИО в деталях ошибок, технических логах и трассировках.

**Что реализовать для закрытия подпункта:**
1. Маскирование email в ошибках (`j***@company.com`).
2. Запрет хранения полного HTML/PII в debug-логах.
3. Разделение operational logs и security audit logs.
4. Настроить retention и удаление логов по политике ИБ.

**Критерий закрытия:**
- Логи не содержат избыточных ПДн; формат соответствует внутренней политике и комплаенсу.

## 4. Надежность отправки и эксплуатация (P0/P1)

### 4.1. Убрать UI-зависимый режим отправки batch
**Что нужно исправить:**
- `i_with_error_screen = 'X'` заменить на серверно-устойчивый режим.

**Что реализовать для закрытия подпункта:**
1. Отправка в background-safe режиме без GUI dependency.
2. Retry policy (например, 3 попытки с backoff).
3. Idempotency key для защиты от дублирования при повторной отправке.
4. Явная модель статусов пакета (`NEW`, `SENT`, `FAILED`, `RETRY`).

**Критерий закрытия:**
- Массовая отправка стабильно работает в фоновом режиме и корректно переживает временные ошибки.

---

### 4.2. Обработка частичных ошибок и отчетность
**Что нужно исправить:**
- Нужна детальная прозрачность по каждому получателю/пакету.

**Что реализовать для закрытия подпункта:**
1. Сохранять результат по каждому email (успех/ошибка/код).
2. Сохранять ошибки транспорта и бизнес-ошибки отдельно.
3. Отображать оператору post-send отчет и возможность выгрузки.

**Критерий закрытия:**
- После отправки доступен полный отчет по статусам без ручного анализа SOST.

## 5. OData/API hardening (P1)

### 5.1. Контракты API и валидация payload
**Что нужно исправить:**
- Усилить входную валидацию всех сущностей.

**Что реализовать для закрытия подпункта:**
1. Валидация обязательных полей (`Subject`, `Recipients`, `HtmlBody`).
2. Лимиты длины строк и количества получателей в запросе.
3. Схемная валидация вложенных коллекций (`Recipients`, `Attachments`, `DocumentLinks`).
4. Единый формат ошибок OData с кодами.

**Критерий закрытия:**
- Некорректный payload отсекается backend-валидацией до бизнес-логики.

### 5.2. CSRF/CORS/SICF security baseline
**Что нужно исправить:**

**Что реализовать для закрытия подпункта:**

2. CORS только для разрешенных origins.
3. Проверка ICF service настроек, отключение лишних endpoint.
4. Верификация TLS-only и корректных cipher policy.

**Критерий закрытия:**
- Сервис соответствует корпоративному baseline SAP Gateway Security.
